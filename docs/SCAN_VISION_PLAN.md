# 📷 房间实景扫描补充方案（方案 C：视觉模型路线）

> 背景：SpatialLM 3D 重建路线（视频→点云→结构化布局）在 RTX 50 系显卡上受阻（torchsparse 内核不兼容，详见 `docs/SPATIALLM_ENV.md`），
> 决定采用**视觉模型路线**作为补充方案：用项目里已验证的视觉能力（LLM_VISION 图文识别 + layout-scan 户型识别模式）实现
> "拍摄房间内景 → 识别家具 → 户型图自动摆放"。
> 更新于 2026-08-31 ｜ 状态：方案设计，待排期

---

## 0. 一句话定位

**不做精确 3D 重建，做"家具清单识别 + 户型图粗摆放"**——手机绕房间拍一圈照片，AI 认出有什么家具、大致在哪个方位，自动落到户型图网格上，用户拖拽微调确认。

---

## 1. 目标 / 非目标

| | 内容 |
|---|---|
| ✅ 做 | 家具类别与数量识别、名称/描述生成、大致方位推断、户型图格点自动摆放、furn 内部模块联动 |
| ❌ 不做 | 精确墙体结构重建、米制尺寸、门窗定位、家具朝向精算（这些是 SpatialLM 的能力域，本方案放弃） |

---

## 2. 预计效果

| 能力 | 预期效果 | 置信度 |
|---|---|---|
| 家具类别识别（床/桌/椅/衣柜/书架…） | 与物品模块图文识别同水平（已实测可用） | 高 |
| 每件家具的粗略方位（东/南/西/北/房间哪一侧） | 依赖拍摄顺序+多帧融合，模糊但可用 | 中 |
| 家具数量（一个房间几张桌几把椅） | 多帧去重后基本准确 | 中 |
| 自动摆放精度 | 格点级粗摆（可能偏差 1~2 格） | 中低 |
| 物品位置链（物品→家具→房间） | 完全打通（复用现有体系） | 高 |

**核心认知：本方案的产出是"AI 摆的草稿"，用户微调是设计内的一环**——不追求一次摆对。

## 4. 接入思路（端到端流程）

```
用户在小程序 layout 页选房间 → 「实景扫描」入口
  → 拍摄模式二选一：
      A. 按引导连续拍照（门口→绕圈，4~8 张）
      B. 录一段视频，小程序端抽帧（每 1~2 秒 1 帧，取 6~10 帧）
  → 帧序列 + 拍摄顺序（隐含方位线索）上传
  → 后端新模块 scan 处理（任务式，异步）：
      ① 逐帧视觉识别 → 每帧家具列表（类别/名称/画面中横向位置/大小占比）
      ② 多帧融合去重：同一家具出现在相邻帧 → 按特征合并（类别+近似位置）
      ③ 方位推断：拍摄顺序（绕圈方向）+ 每帧的家具横向位置 → 相对方位
      ④ 网格映射：家具清单 → 房间网格格点 + furn 模块（见第 5 节）
  → 小程序展示「识别结果预览」：家具清单 + 户型图上的粗摆放
  → 用户一键应用 → 落入户型图编辑器，可拖拽微调（人工确认闭环）
```

**与现有体系联动**：
- 识别出的家具可一键创建为**收纳家具**（furn 模块），物品录入的位置链直接可用
- 识别结果（家具+方位）注入推理引擎知识库，增强"东西放哪了"的推理

## 5. 怎么转换为平面格式（本方案核心难点，三种映射法）

**问题**：照片是 2D 画面，户型图是 2D 俯视网格——缺一个"视角→俯视"的转换。

### 法 A：方位启发式（推荐主方案）

利用**拍摄过程本身携带的方位信息**，无需测距：

1. 拍摄时规定路线：从门口开始，绕房间走一圈（小程序给引导动画）
2. 第 i 帧拍摄方向 ≈ 路线进度角（假设匀速）→ 该帧画面中心指向房间中心
3. 家具在画面中的横向偏移 → 相对视线方向的偏角 → 结合"家具总在房间边界附近"的先验 → 落在房间轮廓边缘的格点上
4. 多帧同家具的角度取均值，收敛出稳定方位

- 优点：零硬件、逻辑简单、可解释
- 缺点：角度有累计误差；对"房间中央的家具"（桌子）判断弱
- 兜底：**每帧同步记录手机指南针方向**（小程序 `wx.onCompassChange` 现成 API，iOS/Android 都支持）→ 方位误差从"假设匀速"降到"真实角度"，大幅提升准确率

### 法 B：人工确认（必备环节，非可选）

识别结果先以**清单形式**呈现（家具+建议方位），户型图上以半透明占位块显示建议位置：

- 用户点「全部应用」→ 按建议格点落位
- 或逐件拖拽到实际位置（拖拽编辑器已具备）
- **这是质量兜底**：AI 摆草稿、人确认，误差由用户在 10 秒内修正

### 法 C：画面包围盒比例估算（可选增强）

视觉模型额外输出家具在画面中的位置与占比（提示词要求 JSON：`{name, x_ratio, y_ratio, w_ratio}`）：

- 横向比例 → 方位角；占比 → 粗略距离（大=近）
- 结合已知房间尺寸（户型编辑器里房间格数）→ 换算格点
- 精度有限，作为法 A 的补充信号

**推荐组合：A（指南针增强）+ C 信号融合 → 自动粗摆 → B 人工微调**。

## 6. 后端接口设计（新增模块 `src/modules/scan/`）

遵循 DEVELOPMENT.md 新增模块模板（service + routes 分层，不跨模块 require）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/scan/rooms/:roomId/photos` | 上传照片帧序列（base64 数组，≤10 帧）→ 创建任务，返回 taskId |
| POST | `/api/scan/rooms/:roomId/video` | 上传视频（可选路径，后端抽帧用 LLM_VISION 同源能力） |
| GET | `/api/scan/tasks/:taskId` | 任务状态：pending/processing/done（复用设备轮询契约模式） |
| POST | `/api/scan/tasks/:taskId/apply` | 将识别结果应用到房间：写入 furn 模块 + 格点占位（返回应用结果） |
| GET | `/api/scan/rooms/:roomId/history` | 该房间历史扫描记录（可回滚） |

- 识别核心复用 `items.vision.js` 的 LLM_VISION 调用（同一 Key、同一提示词工程）
- 未配置视觉 Key 时优雅降级：返回 503 + 引导文案（与 CLIP 降级一致）
- 识别结果落库新表 `scan_tasks` / `scan_results`（迁移追加，只增不改）

## 7. 小程序交互（layout 页）

- 「实景扫描」入口按钮（与「户型图识别」入口并列——两者互补：一个识别结构图纸、一个识别实景家具）
- 拍摄引导页：绕圈路线动画 + 指南针权限申请提示
- 识别中：进度条（轮询任务状态）
- 结果预览页：家具清单卡片（含置信度标记）+ 户型图半透明占位块 → 「应用/取消」
- 应用后跳户型编辑器微调（现有编辑器直接复用）

## 8. 可行性评估

| 维度 | 评估 |
|---|---|
| 技术可行性 | **高**：全部基于现有已验证能力，纯增量开发；无 GPU/新依赖 |
| 关键风险 | ① 方位推断精度（用指南针数据缓解）② 视觉模型幻觉（用"清单+人工确认"闭环兜底）③ 宿舍场景杂乱识别率（提示词限定 59 类家具目录，与 SpatialLM 同词汇表） |
| 工作量估算 | 后端 scan 模块 + 测试：1~2 天；小程序 2 页：1~2 天；联调 1 天 |
| 与现有功能冲突 | 无；与 layout-scan 互补不重叠 |

## 9. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 清单识别 | 后端 `/api/scan/rooms/:id/photos` + 单帧识别返回家具清单 | curl 上传宿舍照片 → 返回合理家具列表 |
| P1 多帧融合 | 去重合并 + 方位推断（拍摄顺序 + 指南针） | 一圈 6~8 帧 → 清单数量不重复、方位基本对 |
| P2 网格映射 | 家具 → 格点/furn 模块写入 + 小程序预览应用页 | 户型图上出现半透明占位，一键应用成功 |
| P3 闭环微调 | 编辑器拖拽微调 + 历史回滚 | 用户从拍摄到修正完成 <2 分钟 |

## 10. 与 SpatialLM 路线的关系（不冲突，可升级）

- 本方案的 `scan` 接口契约（照片序列 → 家具布局）**与 SpatialLM 路线同构**——未来若上云 GPU 跑通 SpatialLM，只需替换 scan 模块的识别实现（照片序列换成视频+点云推理），接口与前端零改动
- `docs/SPATIALLM_ENV.md` / `docs/SPATIALLM_STAGE0.md` 保留存档，作为升级路径的参考资料
